# 独立使用统计页说明

## 背景

管理中心原本已经有：

- `账户管理` 页面，用于管理 client account 与 account-scoped API key
- `AI 提供商` 页面中的近期请求状态条

但没有一个**独立的使用统计页**来统一展示：

1. 账户历史用量
2. 近期请求概览
3. 时间范围筛选后的统计结果

同时，历史上还出现过：

- 旧前端页面调用了已经不存在或不一致的接口路径
- 菜单与页面逻辑混在原有页面里，后续合并时容易被覆盖或丢失

因此，本次改动采用了“**独立路由、独立页面、独立数据层**”的方式实现新的使用统计页，尽量避免继续耦合到 `AccountsPage`，从结构上降低后续合并冲突和功能丢失风险。

---

## 设计目标

本次使用统计页的目标是：

1. 提供一个独立入口：`/usage-stats`
2. 不侵入现有 `AccountsPage` 主体逻辑
3. 只依赖当前后端已经存在的接口
4. 同时展示：
   - 历史账户用量
   - 近期请求概览
   - 汇总指标
5. 支持时间范围筛选
6. 对空数据、异常数据、请求失败都能稳定降级
7. 保持代码文件边界清晰，便于后续单独维护

## 依赖的后端接口

当前页面只依赖以下已存在的后端管理接口：

### 1. 账户列表

- `GET /v0/management/accounts`

作用：

- 读取账户元数据
- 读取账户名、账户 ID
- 读取 account 下的 API Key 元数据
- 为历史用量表补充更友好的展示名称

### 2. 历史账户用量

- `GET /v0/management/account-usage`

支持可选查询参数：

- `from`
- `to`

要求为 RFC3339 时间格式。

作用：

- 获取账户 / API key 维度的历史使用统计
- 作为页面核心表格数据来源

### 3. 近期请求概览

- `GET /v0/management/api-key-usage`

作用：

- 获取 provider 维度的近期请求统计
- 用于生成“近期请求概览”卡片和状态条

## 页面结构

使用统计页由三个主要区域组成。

### 1. 顶部概览卡片

展示聚合后的核心指标：

- 总请求数
- 总失败数
- 总 Token 数
- 活跃账户数
- 活跃 Key 数

这些数据基于 `account-usage` 结果计算得到。

### 2. 历史账户用量

这一部分提供：

- 时间范围筛选
- 自定义起止时间
- 账户/Key 关键字筛选
- 表格展示

表格字段包括：

- 账户
- API Key
- 请求数
- 失败数
- 总 Token
- 最近使用时间

### 3. 近期请求概览

这一部分按 provider 聚合展示：

- provider 名称
- Key 数量
- 成功次数
- 失败次数
- 最近请求状态条

这部分数据来自 `api-key-usage`，与历史账户用量是**不同统计口径**，因此分区展示，不做强行逐行合并。

## 为什么不继续放进 AccountsPage

核心原因是：**避免耦合与避免后续合并丢失**。

如果继续把使用统计写进 `AccountsPage`：

1. 页面职责会继续膨胀
2. 账户 CRUD 与统计逻辑混杂
3. 后续合并时更容易出现冲突
4. 某些旧版本/旧页面切回时更难判断哪部分属于统计、哪部分属于账户管理

现在改成独立页面后：

- 账户管理页继续专注账户与 API Key 管理
- 使用统计页专注统计展示
- 两者只共享后端接口和少量通用组件
- 后续如需下线、替换、重构统计页，只影响独立页面与数据层

## 数据兼容策略

历史用量接口中存在 snake_case 与 camelCase 混用风险，因此工具层做了兼容处理，例如：

- `account_id` / `accountId`
- `account_name` / `accountName`
- `api_key_id` / `apiKeyId`
- `api_key_name` / `apiKeyName`
- `last_used_at` / `lastUsedAt`
- `total_tokens` / `totalTokens`

这样即使后端返回字段风格有历史差异，前端也能稳定渲染。

---

## 竞态保护

使用统计页会在以下场景反复发起请求：

- 切换时间范围
- 自定义时间区间变化
- 页面首次进入
- 手动刷新
- 连接状态切换

为避免旧请求比新请求后返回并覆盖结果，`useUsageStatsData` 中加入了请求序号控制：

- 每次请求生成新的 `requestId`
- 只有“当前仍然是最新请求”的结果才允许写入状态
- 旧请求结果会被丢弃

这样可以避免：

- 快速切换 `24h / 7d / 30d` 后页面显示错乱
- 刷新时旧结果覆盖新结果
- 连接状态变化时的脏状态回写

---

## 空态与降级处理

页面做了以下降级策略：

### 1. 未连接

如果当前未连接服务器：

- 显示提示信息
- 不继续展示误导性的统计结果

### 2. 历史用量为空

如果 `account-usage` 返回空数组：

- 展示“暂无数据”空态
- 不报错，不白屏

### 3. 近期请求为空

如果 `api-key-usage` 没有数据：

- 历史用量区仍然可以正常显示
- 近期请求区独立展示空态

### 4. 近期请求接口失败

如果 `api-key-usage` 请求失败：

- 页面不会整页失败
- 历史用量仍然保留
- 近期请求区单独提示错误或空态

## 与账户页的关系

当前系统中两者分工如下：

### 账户管理页（Accounts）

负责：

- 新增/编辑/删除账户
- 新增/编辑/删除账户级 API Key
- Key 启停
- 历史用量的基础查看（现有页仍保留）

### 使用统计页（Usage Stats）

负责：

- 独立统计视图
- 汇总指标展示
- 时间范围筛选
- 更专门的历史用量表
- provider 近期请求概览

也就是说：

- Accounts = 管理入口
- Usage Stats = 统计入口

## 后续建议

### 1. 增加自动化测试

当前已经完成手工实现与静态校验，后续建议补：

- `buildUsageQuery` 单元测试
- `normalizeUsageRows` 单元测试
- `normalizeProviderCards` 单元测试
- `useUsageStatsData` 的竞态与错误态测试

### 2. 逐步补全高级能力

如果后续需要继续完善，可追加：

- 导出 CSV
- 按账户聚合图表
- 按 provider 聚合趋势图
- 仅查看失败请求
- 仅查看某账户或某 key 的统计
- 更细粒度时间范围快捷选项

### 3. 保持独立边界

后续扩展时建议继续遵守：

- 不回塞进 `AccountsPage`
- 优先在 `features/usageStats/` 下演进
- 新增统计相关逻辑优先放在独立 hook 和 utils 中

这样才能真正降低后续“合并时又丢功能”的风险。
